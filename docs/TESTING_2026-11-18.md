## 1. Get the release and run the offline tests

Run these commands in a terminal on the laptop. The tag identifies the same source on every tester's machine. Keep the printed commit ID with your results.

```sh
git clone --branch v2026.11.18-preview.1 --depth 1 https://github.com/bhanuprakashjh/garuda-pi5.git garuda-pi5-preview
cd garuda-pi5-preview
git rev-parse HEAD
node --version
node --test hosts/pi5/demo/*.test.js
```

**Pass:** the Node test summary shows 197 passed and zero failed. Node 20.19.5 was used for the release check. These tests exercise page logic using fixtures and require no Pi, models or simulator.

To check the receiving tool and board processing with synthetic images, use a Linux terminal in the same checkout. The following creates a local Python environment with test dependencies. Python 3.12 was used on the release workstation.

```sh
python3 -m venv .venv-test
. .venv-test/bin/activate
python -m pip install pytest numpy opencv-python-headless
PYTHONPATH=hosts/pi5:hosts/pi5/oak:bench python -m pytest -q hosts/pi5/test_oak_calibration.py bench/test_oak_receiving_check.py
```

**Pass:** 24 checks pass with zero skips. If OpenCV is skipped, check that `python -c "import cv2; print(cv2.__version__)"` works in the activated environment.

## 2. Check the camera bench

Use a provisioned Pi and its working camera first. A new station needs the matching Hailo driver, runtime and compiled models. Record the existing service configuration before switching camera profiles. The release tag supplies source. Camera services still need to use those files on the Pi. [Pi setup and model inventory](DEMO_USER_GUIDE.md#3-prepare-a-new-pi) · [Camera profile setup](UNIFIED_CAMERA_PROFILES.md) · [OAK USB setup](../hosts/pi5/oak/README.md).

| Enter in the laptop browser | Service |
|---|---|
| `http://PI_HOST:8098/demo` | Camera and detection on the Pi |
| `http://PI_HOST:8099/camera` | OAK calibration on the Pi |
| `http://127.0.0.1:8100/` | Simulator launcher on the laptop |
| `http://127.0.0.1:8099/` | Simulator controller on the laptop |

Replace `PI_HOST` with your Pi's hostname or address. Reload the demo after a page update. Start in **Page simulation**. Move a consenting volunteer into and out of view. Check that the picture changes, the camera label matches the connected device, the people count responds, and processed FPS updates. Save the camera label, source revision and a screenshot. CM3 and USB use a one-lens profile. Continue to step 3 only on the OAK stereo profile.

For a configured OAK, run the following from the checkout on the laptop. Enter your own Pi hostname when prompted.

```sh
read -r -p "Pi hostname or IP: " PI_HOST
python3 bench/oak_receiving_check.py --host "$PI_HOST" --out oak-receipt-01.json
```

**Pass:** eight `OK` lines, exit status 0, and `shipping_profile_observed: true` in the JSON. This verifies advancing camera frames, host stereo and the three served handout files. Use a new output filename for each retry. For a `CHECK`, open the JSON and inspect the named port, error or hash. If only a handout differs, verify which edition is installed. The earlier private transfer kit has a different engineering handout. Use that kit's checkout to verify a kit installation, or install the public calibration assets to verify this tag. Never count a mismatch as a pass.

## 3. Check paired depth and 3D

1. On the OAK demo choose **Depth map**. Wait for the first pair. After four seconds look for changing pair numbers and a rate in **displayed pairs/s**. The large processed FPS readout measures detector work and has a different denominator.
2. Choose **Expand depth**. The RGB and colour depth views should show the same capture. Black pixels mean there was no usable reading. A torso outline appears only when a measurement matches that pair.
3. Close the inspector. **Pass:** the video returns to RGB only and the button reads **Depth map** again.
4. Open **3D view**. Try **Front**, **Top** and **Side**. Drag to orbit, scroll to zoom, double-click to recenter. **Pause** should label the frozen view. Close the tab when finished. The metre grid is a camera-frame reference at lens height.

If the view says **Stale depth** or **Waiting for depth**, record that text, pair number, camera profile and which other tabs were open. For performance comparisons, use the same scene and cooling setup and record both repeats. [Depth-view measurement procedure](OAK_HOST_STEREO.md#comparing-the-depth-views).

## 4. Measure depth against a tape

You need an OAK stereo bench, a flat rigid backing, a ruler, a tape measure and a printer. Use the [printable A4 targets](../hosts/pi5/demo/chennai/oak-targets-a4.pdf) and the [operator's printing and tape-measure instructions](../hosts/pi5/demo/chennai/OPERATOR.md).

1. Print sheet 1 at **100% / Actual size**. Measure both 100 mm scale bars, mount the sheet flat, and measure the printed square pitch. Sheet 1 has **9 × 6 inner corners**.
2. Open **Calibration → Open guided camera calibration** on the Pi. Choose **Depth at measured distances**. Enter measured pitch in **mm** and describe exactly where the tape starts and ends. Set the application's distance tolerance before reviewing results.
3. Collect at least three usable setup placements across near, middle and far. For every capture, read the tape in **metres**, tick the measured-placement box, and record uncertainty in **mm** if known. Keep misses. Choose **Practice** for guessed distances.
4. Reposition and remeasure the board for at least three independent validation placements. Export the ZIP. Match one capture ID across the RGB, raw depth and CSV. In `board-tape-summary.json`, check the eligible and total validation counts. In `board-tape.csv`, inspect each signed difference and the depth coverage.

**Pass for the capture workflow:** the ZIP opens, the setup and validation records are distinct, and every reported difference has a measured reference. **Distance acceptance:** compare the held-out differences and coverage with your predeclared tolerance. Report failures and missing readings. Board results cover the recorded mount, distances and scene. The RGB lens solve produces a candidate and leaves application to a separate review.

## 5. Rehearse the GUI in Gazebo

This check uses a configured Linux laptop, its local PX4 SITL instance, Gazebo and the camera demo. Allow the bench session to finish before testing in a shared lab. The bridge for a physical Ethernet FC is receive-only in this release. Use the isolated laptop simulator with no forwarding route to a physical FC. [PC prerequisites and setup](DEMO_USER_GUIDE.md#4-prepare-the-pc-flight-lab) · [Launcher configuration](DEMO_USER_GUIDE.md#5-configure-and-launch).

1. On the laptop, from the checkout, run `GARUDA_SIM=1 python3 hosts/pc/lab_launcher.py`. Open `http://127.0.0.1:8100/`, check **Setup / paths for this computer**, and confirm the Pi URL.
2. On the **Pi demo page in that laptop's browser**, choose **Fixed camera** for a bench camera and **PX4 on this laptop** as the destination. Click **Start PX4 lab**. Wait for fresh PX4 status showing **disarmed, on ground**. If another tab has control, coordinate with its operator.
3. Release any selected target. **Pass:** the page says **No target selected** and Follow is unavailable. In the simulator choose **Take off**. The expected behavior is Hold with no target. Check the reported arming, ground contact and altitude separately from the request label.
4. Choose **Land**. **Land requested** records the button press. Wait for fresh **disarmed, on ground** from PX4 before disconnecting. If the page reports **Aircraft state unknown**, inspect the laptop controller and wait for fresh telemetry. Keep the test open as unconfirmed until that evidence arrives.

Save the request label, actual PX4 mode, arming and ground-contact state, and the simulator ULog for a failed run. Keep software versions from both machines. GUI takeoff and landing, target loss during physical flight, and physical orbit have no airborne hardware qualification from these tests.

## If a check fails

| Symptom | Next check |
|---|---|
| The GUI looks like the previous release | Reload the tab. From the checkout on the laptop compare one served file with this tag using the commands below. A mismatch means the Pi is serving a different copy. On the Pi, `systemctl show garuda-mono -p ExecStart` identifies the active program path. |
| The camera works but Depth map is missing | Read the camera label. On CM3 or USB this is expected. On OAK check the receiving JSON for the `pi_sgbm_stereo` and `demo_reports_oak_rgb` rows. |
| Calibration opens a flight dashboard | Use the Pi's hostname on port 8099 for calibration. The same port on the laptop belongs to PX4. |
| The board has depth but no tape result | Inspect the CSV comparison status. Check the selected sheet, measured pitch, board flatness, per-placement tape confirmation and valid board pixels. Keep the failed capture. |
| PX4 state is unknown | Open the laptop controller at `http://127.0.0.1:8099/`. Check telemetry there first. If it is fresh there, check the launcher’s configured Pi URL and the browser’s permission to reach the local lab. |

```sh
# On the laptop, with PI_HOST already set in step 2
curl -fsS "http://$PI_HOST:8098/demo/flight-setup.js" -o /tmp/garuda-served-flight-setup.js &&
  cmp hosts/pi5/demo/flight-setup.js /tmp/garuda-served-flight-setup.js
```

A successful comparison exits 0 and prints nothing. Repeat for `controller.js`, `lab.js` and `app.js` when checking a release update.
