Scope: 13 items requested for the Garuda SDK licence gate (CLAUDE.md §1 / §6 rule 6).
Method: every licence read **at source** via WebFetch on 2026-11-12 — the project's own
LICENSE/COPYING file (raw), the repo landing page, and the GitHub/GitLab REST API for
default branch, latest tag, `pushed_at`, SPDX detection, and the last commit touching the

Policy key:
- **SHIP-OK** — BSD/MIT/Apache/LGPL-dynamic; usable in shippable `services/`.

### 10. SuperPoint (magicleap/SuperPointPretrainedNetwork)
- LICENSE title (verbatim): "SUPERPOINT: SELF-SUPERVISED INTEREST POINT DETECTION AND DESCRIPTION — SOFTWARE LICENSE AGREEMENT — ACADEMIC OR NON-PROFIT ORGANIZATION NONCOMMERCIAL RESEARCH USE ONLY". Parties: "your academic institution or non-profit organization or self (called 'Licensee' …) and Magic Leap, Inc." Grant: "a personal, non-exclusive, non-transferable license to use the Software for noncommercial research purposes"; "The Software may be used for your own noncommercial internal research purposes." Prohibits sell/rent/lease/sublicense/lend/time-share/transfer/third-party access. Derivatives: "all and any such derivatives and modifications will be owned by Licensor and become a part of the Software licensed to You."
- **Code vs weights:** the agreement defines "Software" as "the actual copy of all or any portion of code for program routines" plus derivatives; it never names the `.pth` weights. Either way the weights are **not** permissively licensed, and neither is the demo code. The README also states training/evaluation code and the Synthetic Shapes dataset will not be released.
- Correction to prior understanding: it is not "weights research-only, code something else" — **both code and weights are research-only**, and the Licensee definition is academic / non-profit / individual. Whether a corporate bench (Microchip) qualifies as a "Licensee" at all is doubtful → flag to owner. Recommended: do not fine-tune from or ship these weights; prefer XFeat (Apache-2.0) or an independently trained SuperPoint with a verified permissive licence (verify separately — not checked here).
- Verdict: **RESEARCH-ONLY** (stricter than EVAL-ONLY).

### 12. GStreamer
- Canonical repo is on gitlab.freedesktop.org; its raw endpoints are behind Anubis and could not be fetched. The GitHub repo is the official mirror and was used for file text; docs/FAQ/releases on gstreamer.freedesktop.org were fetched directly.
- `subprojects/gstreamer/COPYING`, `subprojects/gst-plugins-good/COPYING`, `subprojects/gst-plugins-bad/COPYING` all read "GNU LESSER GENERAL PUBLIC LICENSE Version 2.1, February 1999".
- **`rtph265pay` lives in gst-plugins-good**: file `subprojects/gst-plugins-good/gst/rtp/gstrtph265pay.c`, header "GNU Library General Public License … either version 2 of the License, or (at your option) any later version" (LGPL-2.0-or-later), Copyright Wim Taymans 2006 / Jurgen Slowack 2014; registers element `rtph265pay` "Payload-encode H265 video into RTP packets (RFC 7798)". Docs page: "Package – GStreamer Good Plug-ins", plugin `rtp`; `rtph264pay` is in the same plugin.
- Official licensing FAQ (read): "We require that all code going into our core packages is LGPL"; "we require the use of the LGPL for all plugins written from scratch or linking to external libraries"; "We do not accept GPL code to be added to our plugins modules"; but "we do accept LGPL-licensed plugins using an external GPL library for some of our plugin modules" — i.e. the plugin file is LGPL but the *effective* licence of a loaded pipeline is LGPL ∪ the linked codec library. Known cases from the docs: `x265enc` → "Package – GStreamer Bad Plug-ins" (links libx265; libx265's own licence not fetched in this pass — verify before use); `x264enc` → "Package – GStreamer Ugly Plug-ins". Patent-pool questions for H.264/H.265 are outside copyright scope and not addressed here.
- LGPL vs GPL split: core/base/good/bad are LGPL-2.1 packages; GPL only enters via externally linked libraries in specific plugins, or -ugly. LGPL-dynamic is satisfied naturally because plugins are dlopen'd `.so` files — keep libgstreamer dynamically linked, ship the LGPL notice, and do not static-link.
- Latest stable: 1.28.9 (6 November 2026). The GitHub tags API returned only the oldest tags (`start`, `monorepo-start`) so it was not useful for currency.
- Verdict: **SHIP-OK** (core + the `rtp` plugin incl. rtph264pay/rtph265pay); per-element allowlist for -bad; GPL-linked encoders and -ugly are EVAL-ONLY. Given the Pi 5 has no hardware encoder (CLAUDE.md §2) and the plan is a USB H.264 camera + payloader, the shipping path stays LGPL.

### 13. Luxonis OAK device firmware / bootloader / model zoo

- **Bootloader:** `depthai-bootloader-shared` is MIT ("Copyright 2020 Luxonis Holding Corporation") but contains only shared headers/src, not the bootloader binary; the binary is pinned as `DEPTHAI_BOOTLOADER_VERSION "0.0.29"` and ships closed like the firmware. (`depthai-shared` is MIT as well.)
- **Model zoo:** `github.com/luxonis/depthai-model-zoo` is MIT but its README says "This repository is deprecated. Please use the new Luxonis Model Zoo instead." Any Ultralytics-derived YOLO there carries AGPL-3.0 (item 11). So: **per-model, check each `model.yml` / HubAI card** before use.
- Verdict: host SDK SHIP-OK (items 1–3); **firmware + bootloader binaries UNCLEAR** — using an OAK as a purchased peripheral that runs Luxonis' own firmware is the normal case, but *redistributing* the firmware/bootloader blobs in a product image needs written terms from Luxonis. Owner action: ask Luxonis for the firmware/bootloader redistribution terms (or an EULA reference) before Phase 8.
